# App Attest & identity keys — reference

Companion to `architecture-decisions.md` (product/protocol) and
`attestation-assertion-workflow.md` (step-by-step flow). This doc answers a
narrower question those two don't spell out explicitly: what a `keyId`
actually is, how it relates to `account_uuid`, and exactly how many distinct
keypairs this system involves.

Last updated 2026-09-18.

---

## 1. What `keyId` is

`DCAppAttestService.shared.generateKey()` asks the **Secure Enclave Processor
(SEP)** — a separate hardware coprocessor with its own hardware RNG, isolated
from the main CPU — to generate an **ECDSA P-256 keypair**. This happens
**entirely on-device, with no network call**. The private key never leaves
the SEP: it isn't exportable, isn't readable by the app process, and every
signing operation that uses it (`attestKey`, `generateAssertion`) happens
*inside* the enclave — only inputs go in and results come out.

`generateKey()` does not return the raw public key. It returns `keyId`, a
string computed as `SHA256(DER(publicKey))` — a compact fingerprint the app
uses to tell the SEP "operate using this key" in later calls. The actual
public key bytes only appear later, embedded in the certificate returned by
`attestKey()`.

## 2. Local generation vs. Apple's servers

| Call | Where it runs | Network? |
|---|---|---|
| `generateKey()` | SEP only | No — pure local silicon operation |
| `attestKey()` | SEP + Apple's attestation servers | Yes |

`attestKey()` is where the network dependency lives. Apple's servers perform
some authenticity/risk evaluation as part of deciding whether to issue a
certificate for this key — this is why `attestKey()` (unlike `generateKey()`)
can fail transiently with things like `serverUnavailable`, and why key
generation is rate-limited per device over its lifetime: Apple is gating how
many certificates it will issue, not how many local keys can exist.

## 3. `keyId`, `attest_pubkey`, and `account_uuid` — how they relate

There is **one** public key in play here, referenced two different ways.
`keyId` and `attest_pubkey` are not two different keys:

```
SEP generates ──► private key (stays in SEP forever, never exported)
                   public key
                        │
                        ├── SHA256(DER(public key)) ──► keyId
                        │     (compact handle, returned by generateKey())
                        │
                        └── embedded in the leaf certificate of the
                            attestKey() attestation object ──► attest_pubkey
                            (the literal key bytes, extracted server-side)
```

At registration, once the server verifies the attestation chain, the nonce
binding, `rpIdHash`, and `keyId == SHA256(publicKey)`, it **mints a fresh
`account_uuid`** and persists exactly one row:

```
{ account_uuid, key_id, attest_pubkey, counter: 0 }
```

`account_uuid` is a server-assigned alias for that `(key_id, attest_pubkey)`
pair — it exists so the app and contacts have a stable, opaque routing handle
that isn't itself the raw device credential. **`identityPublicKey` (the
user-facing identity key — see §4) is not in this row.** It's used only
transiently, to verify the nonce binding at registration time, then
discarded (workflow doc step 10; architecture doc §10 explains why: it's the
most graph-linkable value the server could hold, so it never persists it).

```
Secure Enclave key ──(SHA256)──► keyId ──(minted once, 1:1)──► account_uuid
       │
       └─(public half)──► attest_pubkey  ←── what assertions get verified against
```

## 4. Every keypair in the system

Scoped to registration + attestation. The Noise/Double Ratchet layer
introduces its own ephemeral X25519 keys per conversation — a separate,
later concern, not covered here.

| # | Keypair | Curve | Generated by | Private key lives | Public key |
|---|---|---|---|---|---|
| 1 | App Attest key | ECDSA P-256 | SEP, on-device | SEP only, never leaves | = `attest_pubkey`, hashed as `keyId` |
| 2 | Identity key | X25519 | App, in software (CryptoKit) | Keychain, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` | `identityPublicKey` — shown to the user as the identicon/word-triple, exchanged directly with contacts during pairing, sent to the server once and discarded |
| 3 | Apple's App Attest CA | — | Apple (not generated by the app or server) | Apple's HSMs | Published root/intermediate certs — the server validates the `x5c` chain against this; never generates or stores a private counterpart |

Two keypairs the app is actually responsible for (#1, #2), on deliberately
different curves, plus one trust anchor (#3) only ever verified against. #1
and #2 are never merged into a single key — the only place the two systems
touch is `clientDataHash = SHA256(challenge ‖ identityPublicKey)`, which the
App Attest key signs over. That hash is the sole binding between "this is a
genuine, unmodified app on real hardware" (App Attest) and "this is the
identity the user is registering" (the X25519 key) — deliberately a one-way
hash, not a shared key, so the two systems stay independent.

## 5. The assertion flow — how the server authorizes each session

Runs on every authenticated request, forever, and is deliberately thin: no
retries, no state machine (workflow doc Part 2).

1. App fetches a fresh nonce (`GET /session/nonce`, 60s TTL — much shorter
   than the 15-minute registration challenge, because nothing is cached
   against it).
2. App builds `payloadHash = SHA256(nonce ‖ body)`, where `body` includes the
   claimed `account_uuid`.
3. App asks the module to sign it (`coordinator.sign(payloadHash)`), which
   calls `generateAssertion(keyId, clientDataHash: payloadHash)`. The SEP
   produces an ECDSA signature with the same private key proven genuine at
   attestation time, and bakes in a **monotonically incrementing counter**
   automatically — the app and module never touch it directly.
4. App sends `POST /session` with `{assertion, nonce, body}`.
5. Server verifies, in order:
   - nonce valid and unconsumed (blocks replay against a stale nonce)
   - `SHA256(nonce ‖ body)` matches what the assertion signed (blocks
     tampering with the body after signing)
   - the ECDSA signature verifies against the **stored `attest_pubkey`** for
     this account — the actual proof: only the device holding that exact SEP
     key can produce a valid signature
   - the counter is strictly greater than the last one stored, then persists
     the new value (blocks replaying a captured old assertion)
6. Server issues a short-lived session token, which — not the assertion
   itself — gates the rest of the connection.

The server never re-proves "genuine hardware, unmodified app" per session;
that was a one-time cost paid at attestation. Per session it only proves
"whoever's asking still holds the exact SEP key that was proven genuine, and
this isn't a replayed old request" — cheap (~50–100µs ECDSA verify) precisely
because the expensive proof already happened once and the SEP key can't be
extracted or cloned.
